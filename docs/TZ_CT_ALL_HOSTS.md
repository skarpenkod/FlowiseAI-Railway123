# ТЗ: сбор всех имён хостов из логов Certificate Transparency

## Цель

Написать и запустить на VPS сборщик **всех имён хостов** из логов Certificate Transparency (CT) за всю историю CT. Цель — максимальное число уникальных хостов.

Результат:
- `ct_hosts.parquet` — каждый уникальный хост один раз, с признаками китайского сегмента;
- `ct_domains_cn.parquet` — китайский срез из того же прохода.

Ориентиры, оценка грубая:

| | Записей | Уникальных хостов | Трафик |
|---|---|---|---|
| Текущие шарды | ~46 млрд | ~0,5–2 млрд | ~55 ТБ |
| Все логи за всю историю | сотни млрд | несколько млрд | сотни ТБ |

## Стек

- Python 3.11+, pyarrow, duckdb, tldextract.
- HTTP: stdlib `urllib` или `httpx`.
- Только бесплатные источники, без платных API.
- Логи пишутся в stdout.

## 1. Список логов

- Источник: `https://www.gstatic.com/ct/log_list/v3/all_logs_list.json`.
  - `operators[].logs[]` — классические RFC 6962, поле `url`;
  - `operators[].tiled_logs[]` — static-ct-api (tiled), поле `monitoring_url`.
- Брать **все** логи и шарды любых лет в любом состоянии: `usable`, `qualified`, `readonly`, `retired`, `rejected`.
- Без ограничения по времени: каждый лог читается с индекса 0 до `tree_size`.
- Сначала проверить доступность каждого лога (`get-sth` / `checkpoint`).
  - Недоступные логи записать в отчёт.
  - Для недоступных поискать публичные архивы (например, `github.com/geomys/ct-archive` и аналогичные зеркала). Если архив есть — добавить загрузчик из архива с тем же разбором записей и теми же чекпоинтами.
- Медленные RFC 6962-логи (Google Argon\*, Xenon\* и т.п.) **не исключать**.
  - Они идут параллельно со всеми остальными, с низким приоритетом.
  - Их лимиты соблюдать: на 429 ждать, учитывать `Retry-After`.
  - **Не обходить лимиты ротацией IP.**
  - Читать сколько успеется, с чекпоинтом.
- Порядок чтения: сначала самые свежие шарды (это живые сайты), затем исторические, от новых к старым.
- Параметры:
  - `--logs` — `all` или подстроки имён/URL через запятую;
  - `--exclude` — то же, для исключения;
  - `--shard K/N` — см. п. 6.

## 2. Протоколы

### RFC 6962

- `GET <url>ct/v1/get-sth` → `{"tree_size": N}`.
- `GET <url>ct/v1/get-entries?start=a&end=b`, где `b` включительно.
  - Сервер может вернуть меньше записей, чем просили (обычно 32 или 256). Дозапрашивать в цикле.
- `entries[].leaf_input` (base64) — структура `MerkleTreeLeaf`:

```
version u8, leaf_type u8, timestamp u64 (мс), entry_type u16,
entry_type = 0: сертификат                       (длина u24 + DER)
entry_type = 1: issuer_key_hash [32] + TBSCertificate (длина u24 + DER)
extensions                                       (длина u16 + байты)
```

### static-ct-api (tiled)

- `GET <monitoring_url>checkpoint` → текст, вторая строка — `tree_size`.
- Тайлы по 256 записей: `GET <monitoring_url>tile/data/<path>`.
  - `path` — номер тайла группами по 3 цифры; все группы, кроме последней, с префиксом `x`.
  - Примеры: `5` → `005`, `1234067` → `x001/x234/067`.
- Последний неполный тайл: `tile/data/<path>.p/<W>`, где `W` — число записей в нём (1..255).
- **Подводный камень:** на ещё не заполненный полный тайл серверы отвечают не только 404, но и **403** (так делает Let's Encrypt с хранилищем S3). На 403 или 404 сразу запрашивать `.p/<W>`, без ретраев.
- Ответ может прийти в gzip (`Content-Encoding: gzip` или первые байты `1f 8b`) — распаковать.
- Запись в тайле (`TileLeaf`), записи идут подряд до конца файла:

```
timestamp u64, entry_type u16,
entry_type = 0: cert (u24 + DER), extensions (u16), chain_fingerprints (u16)
entry_type = 1: issuer_key_hash [32], tbs (u24 + DER), extensions (u16),
                pre_certificate (u24 + DER), chain_fingerprints (u16)
```

## 3. Разбор сертификата

- Написать свой минимальный DER-парсер. Библиотека `cryptography` не разбирает голый TBSCertificate из precert-записей и слишком медленная.
- Что достать из Certificate или TBSCertificate:
  - **issuer** — 3-й элемент TBS после необязательного `[0] version`; брать O, если его нет — CN;
  - **subject** — 5-й элемент; нужны CN (`2.5.4.3`), C (`2.5.4.6`), O (`2.5.4.10`);
  - **subjectAltName** (`2.5.29.17`) внутри `[3] extensions` — все dNSName (тег `0x82`).
- Имена хоста = SAN + CN.
- Цель по скорости: от 10 тыс. записей/с на ядро.

## 4. Нормализация

- Нижний регистр, без ведущих `*.`, без точки в конце, IDN переводится в punycode.
- Невалидные хостнеймы отбрасываются.
- `domain` (eTLD+1) **не считать на лету**. Он вычисляется в конце, по уникальным хостам:
  - tldextract на локальной копии PSL (`https://publicsuffix.org/list/public_suffix_list.dat`, `include_psl_private_domains=False`);
  - параллельно в несколько процессов.

## 5. Признаки

Сохраняются для каждого хоста. **Ничего не отбрасывать.**

| Признак | Тип | Условие |
|---|---|---|
| `cn_tld` | bool | зона `.cn` или `.xn--fiqs8s` (`.中国`) |
| `china_list` | bool | хост или его родитель есть в [accelerated-domains.china.conf](https://raw.githubusercontent.com/felixonmars/dnsmasq-china-list/master/accelerated-domains.china.conf) (строки `server=/domain/IP`; скачивать при каждом запуске) |
| `cn_org` | bool | хоть один сертификат хоста выдан на владельца с `C=CN` |
| `cn_issuer` | bool | хоть один сертификат от китайского УЦ: TrustAsia, WoTrus, CFCA (China Financial Certification Authority), Xin Net, GDCA, SHECA, CNNIC, vTrus, iTrusChina. Список держать в конфиге. |
| `issuers` | list | до 5 разных издателей |

## 6. Архитектура и дедупликация (главное)

Строк вида «хост × запись» будет больше 100 млрд, хранить их нельзя. Дубли схлопываются по ходу работы.

**Процессы и потоки**
- Каждый лог обрабатывается в отдельном процессе (multiprocessing).
- Внутри процесса — пул потоков для HTTP, `--workers`, по умолчанию 16.
- Число одновременных логов — `--procs`, по умолчанию 40. Процессов больше, чем ядер, потому что медленные логи ждут сеть, а не CPU.

**Сброс данных на диск**
- Процесс копит словарь `host → (min_ts, max_ts, count, флаги, issuers)` на чанк из 1–2 млн записей.
- При сбросе строки раскладываются по 256 бакетам по хешу host.
- Part-файл пишется атомарно (сначала tmp, потом rename): `work/parts/<bucket>/<лог>-<from>-<to>.parquet`.
- **Только после этого** сдвигается чекпоинт `work/state/<лог>.json` с полями `{start, next}`.

**Компактор**
- Отдельный процесс. Когда в бакете накопилось больше N part-файлов, DuckDB сливает их в один:
  - группировка по host;
  - min/max по ts, сумма count, `bool_or` по флагам, объединение issuers (до 5).
- Работа идемпотентна: сначала пишется новый файл, потом удаляются старые. Каждый шаг фиксируется в журнале `work/compact.log`.
- Так диск не растёт бесконтрольно.

**Ошибки сети**
- На 429, 5xx и обрывы — экспоненциальная пауза с учётом `Retry-After`.
- Если окно не скачалось после 5 попыток: сохранить чекпоинт и завершить этот лог с ошибкой.

**Продолжение после остановки**
- После падения или перезагрузки запускается **та же команда**. Сбор продолжается с чекпоинтов, без потерь и дублей.
- При повторном запуске каждый лог читается до своего текущего `tree_size`: живые логи продолжают расти.
- `--hours N`: через N часов сохранить все чекпоинты и выйти.

**Несколько серверов**
- `--shard K/N` делит список логов на N частей с примерно равным суммарным `tree_size`.
- Каждый сервер пишет свои part-файлы.
- `--merge` сливает результаты нескольких серверов в один `ct_hosts.parquet`.

**Вывод в stdout**
- Каждые 1–2 млн записей: лог, позиция/конец, записей/с, ETA.
- Раз в 10 минут: сколько прочитано всего, размер `work/`, число бакетов и файлов.

## 7. Результат

Финальный шаг `--finalize`:
- по каждому бакету `GROUP BY host`;
- вычислить `domain`;
- записать Parquet (zstd). Допустим набор файлов `ct_hosts/part-XXX.parquet`.

### `ct_hosts.parquet`

| Колонка | Тип | Что это |
|---|---|---|
| `domain` | string | eTLD+1, punycode |
| `host` | string | полное имя, уникально |
| `source` | string | всегда `ct` |
| `first_seen` | date | min(ts) |
| `last_seen` | date | max(ts) |
| `hits` | int64 | число записей в логах. Это примерно число сертификатов × 4: каждый сертификат лежит в 2+ логах и записан в двух версиях (precert и финальный). |
| `cn_tld`, `china_list`, `cn_org`, `cn_issuer` | bool | признаки из п. 5 |
| `extra` | json | `{"issuers": [...]}` |

### `ct_domains_cn.parquet`

- Строки, где хотя бы один из `cn_*` признаков равен true.
- Колонки: `domain, host, source, reason, first_seen, last_seen, hits, extra`.
- `reason` берётся по приоритету: `cn_tld` > `china_list` > `cn_org` > `cn_issuer`.

## 8. Проверка (validate.py)

Проверить в обоих файлах:
- нет дублей `host`;
- нет NULL в обязательных колонках;
- `host` нормализован и либо равен `domain`, либо заканчивается на `"." + domain`;
- `first_seen <= last_seen`;
- `hits >= 1`;
- `extra` — валидный JSON.

Контрольный список, все домены должны найтись:
google.com, facebook.com, wikipedia.org, baidu.com, qq.com, sina.com.cn, taobao.com, tmall.com, jd.com, 163.com, weibo.com, bilibili.com, zhihu.com, alipay.com, aliyun.com, douyin.com, meituan.com, xiaomi.com, huawei.com, 12306.cn.

## 9. Порядок работы

1. **Код и тесты.** Поднять локальный фейковый RFC 6962-лог и фейковый tiled-лог с синтетическими сертификатами и precert. Тесты должны покрывать:
   - неполный тайл;
   - ответ 403 на неполный тайл;
   - gzip;
   - полный цикл, включая прерывание посередине и продолжение без дублей;
   - компакцию.
2. **Замер.** Один лог Let's Encrypt (Sycamore или Willow текущего полугодия), свежие 2 млн записей. Сообщить:
   - записей/с;
   - вывод `nproc`;
   - сколько уникальных хостов на 1 млн записей.
3. **Этап 1 — текущие шарды.** Запуск в tmux или systemd. Ожидаемо 5–7 суток при 1 Гбит/с. Затем `--finalize` и сдать промежуточный `ct_hosts.parquet`.
4. **Этап 2 — исторические шарды и архивы.** От новых к старым. Займёт недели. Если серверов несколько — делить через `--shard`.
5. **Завершение.** Когда у всех логов ETA 0:
   - запустить ещё раз, чтобы дочитать записи, появившиеся за время прогона;
   - `--finalize`;
   - `validate.py`.

## 10. Сервер

- Один сервер: от 32 ядер, 64 ГБ RAM, 4 ТБ NVMe, 1–10 Гбит/с.
- **Входящий трафик безлимитный:** придут сотни ТБ. Облачные тарифы с лимитом трафика не подходят.
- Несколько серверов с `--shard` ускоряют сбор пропорционально их числу.

## 11. Что сдать

- `ct_hosts.parquet` — все хосты;
- `ct_domains_cn.parquet` — китайский срез;
- полный лог запуска;
- вывод `validate.py`;
- отчёт:
  - сколько записей прочитано по каждому логу;
  - какие логи недоступны и какие взяты из архивов;
  - сколько заняло времени;
  - число хостов и доменов всего и в китайском срезе.
